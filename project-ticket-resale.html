The Problem

Ticket resale today runs almost entirely on trust with no verification behind it. A buyer sees a listing, pays, and hopes the ticket is real — there's no way to check a seller's history, no way to know if the same ticket has already been sold twice, and no way to prove a ticket is genuine at the door. Scalpers post duplicate listings for tickets they don't have, take the money, and disappear before anyone notices. On the seller side, legitimate fans trying to resell a ticket they genuinely can't use get lumped in with fraudsters, because platforms have no fast way to tell the two apart at scale.

The goal wasn't just "build a marketplace" — it was to build one where trust is computed, not assumed, and where a ticket's authenticity can be verified in seconds, not disputed after the fact.

The Build

Built completely solo — every line of code, every deployment, every bug fixed at 2am. This project taught me more about how real systems are built than anything else I've worked on. Here's what each piece actually does and why it exists:

  • ML Fraud Detection — every new listing is passed through a Scikit-learn model running as its own Flask microservice. It looks at signals like price deviation from market average, how old the seller's account is, and how many listings they've posted that day, and returns a trust score before the listing ever goes public. High-risk listings get flagged for review instead of shown to buyers straight away — this is the "before buyers see them" part that actually prevents the fraud, rather than just detecting it afterward.
  • Real-Time with Socket.io — the moment a ticket is purchased, a WebSocket event fires from the Node API to every connected client, and that listing disappears from everyone's screen instantly. This solves the classic double-booking problem where two buyers both try to purchase the last ticket at the same time — without WebSockets, you'd need constant polling or risk selling the same ticket twice.
  • Two Databases, Split by Purpose — MongoDB Atlas holds the transactional data (users, tickets, orders) because it's fast for the read/write patterns a live marketplace needs. PostgreSQL on Supabase holds analytics data separately, because running heavy reporting queries against the same database serving live traffic would slow down the actual app. Splitting them means the marketplace stays fast even while analytics queries run in the background.
  • JWT Auth + QR Verification — every purchase generates a unique, single-use QR code cryptographically tied to that specific buyer and ticket. At the event, the QR is scanned once — after that, it's invalid, which blocks the common scam where a seller screenshots and resells the same ticket to multiple buyers.
  • 3 Services Deployed Independently — the React frontend, Node.js API, and Flask ML service are each their own deployment (Vercel, Render, Render). This means the fraud-detection model can be retrained and redeployed without touching the live frontend or API, and if the ML service ever goes down, the core marketplace keeps working — it just skips the fraud check gracefully instead of crashing.

The Outcome

The platform shipped as three independently deployed, independently scalable services, with real-time listing updates that eliminate double-booking and an automated fraud layer that catches high-risk listings before a human ever has to review them. Because the fraud check runs as its own microservice, the marketplace stays responsive even under load — the ML scoring happens asynchronously and doesn't block a listing from loading.

Beyond the app itself, this was the project where I learned to actually operate a multi-service production system solo: coordinating deploys across three separate platforms, handling a service going down without taking the whole app with it, and debugging real-time bugs that only show up with multiple concurrent users. It's live, it's public, and I'm actively open to feedback from the community — and to SDE / full-stack roles.
